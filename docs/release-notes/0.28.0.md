# 0.28.0

**Released:** November 13, 2026. [GitHub release](https://github.com/Trendyol/stove/releases/tag/v0.28.0).

Stove 0.28.0 adds continuous JVM and Go profiling to the existing Stove Server. Enable the JVM profiler in the tracing Gradle plugin or configure the native Go wrapper, run your end-to-end tests, and use **Drill Down** or MCP to investigate sampled CPU cost, allocation pressure, surviving objects, and lock waits. No separate Pyroscope backend or additional deployed service is required.

This release also adds managed database chaos with named fault/recovery experiments, Cucumber suspend steps, and Quarkus Bridge for direct CDI bean access from end-to-end tests.

## Cucumber suspend steps (incubating)

`stove-extensions-cucumber` runs Gherkin feature files with public Kotlin suspend
steps using Stove's `Given`/`When`/`Then` annotations and the existing `stove {}` DSL.
Cucumber retains discovery, argument conversion, tags, and scenario execution.
The backend carries Stove, reporting, and tracing through coroutine suspensions.

The Cucumber, Kotest, and Jupiter adapters share `stove-extensions-common` for the
reporting lifecycle. Failed scenarios receive a plain-text diagnostic attachment.
Parallel scenarios and outline rows have isolated report and trace sessions; the
example enables parallel execution by default. Lifecycle hooks use native
synchronous Cucumber annotations.

See the [Cucumber guide](../testing-styles/cucumber.md) and the new
[example](https://github.com/Trendyol/stove/tree/main/examples/cucumber-example).
The bundled Stove skill includes a focused Cucumber setup and troubleshooting guide.

## Quarkus Bridge

`stove-quarkus` now provides `com.trendyol.stove.quarkus.bridge`. Register `bridge()` before the Quarkus runner, then use `using<T>` inside `stove {}` to access beans from the running application's ArC container.

- Supports default CDI qualifiers and generic bean types. Missing or ambiguous beans produce actionable errors.
- Requires an augmented uber-jar first on the test runtime classpath, with raw main output excluded. The isolated fast-jar launcher does not support Bridge.
- Preserve beans referenced only by tests with `%e2e.quarkus.arc.remove-unused-beans=false` as a fixed e2e build default. This is a build-time setting; runtime parameters alone cannot restore removed beans.
- Dependent instances are destroyed at `Stove.stop()`. Request scopes must already be active; Bridge does not activate them automatically.

The bundled Stove skill now includes a focused Quarkus Bridge guide covering Gradle classpath setup, bean preservation, lifecycle, and troubleshooting. See [Quarkus Bridge setup](../frameworks/quarkus.md#bridge) and the [quarkus-bridge integration fixture](https://github.com/Trendyol/stove/tree/main/starters/quarkus/tests/quarkus-bridge) for the working configuration and verification tests.

## Quarkus startup detection

Stove now waits for Quarkus lifecycle startup completion in both direct and fast-jar modes. Headless applications need no HTTP endpoint or custom readiness bean. Existing `StoveStartupSignal` beans and `stove.quarkus.ready` properties can be removed. Startup failures propagate to tests without terminating the test JVM, and the existing startup timeout still applies.

## Continuous JVM profiling

- Opt-in `stoveTracing.profiling` configuration attaches Pyroscope Java agent **2.9.2** to selected Gradle test JVMs. CPU sampling is enabled with profiling; allocation, live-allocation, and lock sampling are optional.
- Collection starts with the dashboard run ID, carries service/instance identity, and flushes the final partial recording on orderly teardown. Profiling can run independently of OTel Java-agent instrumentation.
- When tracing and profiling are enabled together, the plugin loads the bundled Pyroscope OTel extension 2.1.4 for local root span correlation. `profiling.traceCorrelation=false` opts out; Stove retains startup, identity, final flush, and shutdown ownership. Downstream builds need no extra repository or direct GitHub access.
- Profiles upload directly to Stove Server over HTTP or HTTPS using Pyroscope Java's JFR multipart contract. `profiling.serverUrl` is configured separately from dashboard event ingestion.
- Grafana's Apache-2.0 JFR parser is embedded in the Rust server via a Go archive. Recordings use the existing SQLite or PostgreSQL storage, bounded conversion/query budgets, per-run retention, and the normal run purge lifecycle.
- Shared frame definitions reduce normalized recording size for deep allocation stacks. Upload retries are idempotent.

See [Profiling and Drill Down](../observability/profiling.md) for version-catalog setup, configuration defaults, HTTPS deployment, and resource limits.

The [shared-server deployment guide](../observability/profiling.md#shared-stove-server-over-https) includes both client destinations, CI configuration, gateway routes and prefixes, identity headers, body limits, timeouts/retries, JVM certificate trust, authentication support, and end-to-end verification.

## Drill Down

The dashboard adds **Drill Down · whole run** for performance investigation:

- CPU and allocation metric cards with readable totals, service selection, and recording-window filtering.
- Searchable flame graphs, frame details, zoom navigation, and zoom preserved across refreshes.
- Hottest-method tables ranked by self or inclusive cost, linked to frame highlights.
- Recording duration, stack record counts, graph coverage, omitted-stack explanations, and sampled-evidence findings.
- Span details can open Drill Down for a correlated local root span or its trace, with explicit scope, empty-sample guidance, and a return to the entire run.
- Live refresh, recoverable error and empty states, and layouts for light and dark themes.

Test selection includes whole recordings overlapping that test, including background work. It does not turn sampled profiles into exact per-test attribution.

## Profiling evidence for agents

`stove_profiles` preserves trace/span selectors in follow-up calls. Use a span’s `pyroscope.profile.id` as `span_id`; arbitrary child spans and asynchronous thread transitions are not guaranteed to have correlated samples.

`stove_profiles` exposes run-scoped hotspots, units, sampling settings, recording windows, findings, and source profile IDs. An optional baseline returns evidence from another run of the same application using run-wide service/metric selectors. `stove_diagnose` includes a run-wide profile summary, even when diagnosing one test.

The bundled Stove skill gains a dedicated profiling guide for configuration, runtime support, HTTPS ingestion, IntelliJ/Gradle execution, and evidence-driven investigation. See [MCP profiling evidence](../Components/21-mcp.md#profiling-evidence).

## Runtime support and interpretation

This release supports **JVM JFR and native Go pprof profiles**. The Gradle plugin profiles the test JVM and applications running inside it. The new `go/stove-profiler` module wraps `pyroscope-go` 1.5.0 and starts only when configured. `DashboardExternalProfilingOptions` supplies the exact run identity to process/container environment mappers, as demonstrated by the Go showcase.

Go CPU, allocation, heap, goroutine, mutex, and block evidence uses the existing Drill Down and MCP queries. Snapshots use the latest recording per instance and metric; interval deltas accumulate. The Go wrapper supports custom authentication headers and HTTP clients, bounded retries, and graceful final flushing without forced GC. See [Go developers](../observability/profiling.md#go-developers).

Python, Node.js, Rust, arbitrary cumulative pprof files, Pyroscope Push RPC, and OTLP Profiles are not supported. Separate JVMs and already deployed applications still need custom agent/lifecycle integration.

Allocation profiles indicate memory pressure. Live profiles use the latest recording per instance and report sampled surviving objects, not retained heap or reference paths. Neither high CPU share nor surviving allocations prove a defect, regression, or memory leak. Compare equivalent workloads and corroborate findings with source and heap/GC evidence.

## Container shutdown

Container runners now ask Docker to stop the application within `gracefulShutdownTimeout` before Testcontainers removes it. This lets signal handlers flush profiles and other buffered evidence; previously cleanup could kill the application immediately. Applications that ignore the stop signal are still terminated after the timeout.

## Named chaos experiments and directional stalls

- `chaosExperiment(name, fault, timeout, baseline, faulted, recovery)` reserves the application route before baseline,
  executes each phase once, waits for its child coroutines, heals before recovery, and reports named phases under one
  finite coroutine deadline. Standalone faults on the route are rejected while the experiment runs.
- `stall(direction)` supports request-only and response-only stalls, defaulting to both directions.
- `awaitStalledTraffic(timeout)` waits for bytes encountered by the current stall; `sendIntoStall(timeout) { ... }`
  starts a request in the background and returns its pending result after route-wide stall evidence is observed. Earlier
  or unrelated traffic within that fault can satisfy the wait; it does not identify the request. Evidence does not survive
  healing or a new fault, and does not replace direct persisted-state assertions.
- Fault and experiment blocks receive the faulted system as their parameter (`duringFault { redis -> ... }`), and
  route reservations last until the enclosing `stove { }` block exits.
- An executable HTTP/Redis recovery test verifies atomic operation-ID deduplication across committed-but-unacknowledged
  writes, bounded application retries, and fresh operations after healing.

For callers adopting the pre-release model directly, `NetworkFault.Stall` is now a value with a direction:
use `NetworkFault.Stall()` or `stall()` for the previous bidirectional behavior. Recompile consumers of the changed API.

## System-local database chaos

Elasticsearch, PostgreSQL, MySQL, SQL Server, Redis, MongoDB, and single-node Cassandra can route the application's database connection through a
Stove-managed TCP proxy. Enable it on the system's options, then inject faults inside that system's validation
block:

```kotlin
import com.trendyol.stove.chaos.enableChaos

Stove().with {
    elasticsearch {
        ElasticsearchSystemOptions(
            configureExposedConfiguration = { cfg ->
                listOf("search.url=http://${cfg.host}:${cfg.port}")
            }
        ).enableChaos()
    }
    // Register your application runner here.
}.run()
```

```kotlin
stove {
    elasticsearch {
        duringFault {
            // Ordinary cross-system assertions while the application's connection is unavailable.
        }
        // Recovery checks; the route remains reserved until this system block exits.
    }
}
```

`duringFault` defaults to `NetworkFault.Unavailable`; `stall()` and `latency(duration, direction)` are also available.
Stove retains direct database access and restores connectivity on completion, failure, or cancellation. Fault application
and restoration appear in reports. Managed proxy startup rollback and shutdown are owned by Stove.

The initial adapters support specific single-endpoint topologies. Cassandra is limited to a fixed single-node container;
Couchbase is not included. See the
[chaos guide](../chaos-testing.md#supported-systems-and-routing-limits) for discovery, TLS, provided-instance, and
container-networking restrictions.

## Redis database selection

Stove's native Redis client now honors the configured database number for migrations and direct assertions. Previously
it connected to database `0` even when the options selected another database (the default is `8`). Configure the application
client to use the exposed `database` and `password` alongside `redisUri` where needed: the URI from `RedisOptions.provided`
contains only the host and port. URI-only application configuration may still select database `0` or omit authentication.
Verify an application write with a direct Stove read on the selected database before removing selection workarounds. Set
`database = 0` explicitly if the suite intends to use database `0`.

## Opt in through database options

`elasticsearch`, `postgresql`, `mysql`, `mssql`, `redis`, `mongodb`, and `cassandra` keep their existing
`() -> Options` setup callbacks, for both keyed and unkeyed registrations. Their JVM `Function0` signatures,
options constructors, `provided(...)` factories, and migration APIs are preserved. Existing saved factories,
function references, shared helpers, and Java callback shapes continue to work.

The supported options implement `SupportChaos`. Import `com.trendyol.stove.chaos.enableChaos` and chain the opt-in
on the options returned by the setup block:

```kotlin
import com.trendyol.stove.chaos.enableChaos

val makeOptions: () -> ElasticsearchSystemOptions = { existingOptions }

// Existing setup remains valid.
elasticsearch(makeOptions)

// Opt in for a subsequent registration.
elasticsearch(Dc1) { makeOptions().enableChaos() }
```

`enableChaos()` returns the same concrete options instance, including provided-instance subclasses. It can be
chained before or after `migrations { ... }`. Like migration configuration, it changes the options in place.
The setting is read during registration; later changes do not reconfigure systems already registered. Build
separate options when registrations need different settings.

Keep the application wired from `configureExposedConfiguration`. With chaos enabled, that callback receives the
application-facing endpoint. The system's own native client, migrations, and validation DSL retain direct configuration.
For MongoDB, use the exposed connection URI to retain the adapter's required direct-connection mode.

### Move manual experiments only when adopting managed routing

Replace the setup-time `proxy.start(...)` and proxy URL substitution with `options.enableChaos()` and the usual exposed
configuration. Replace `withNetworkPartition(proxy) { ... }` with `duringFault { ... }` inside the selected system's
validation block. Remove manual proxy shutdown only after that proxy is no longer used.

The low-level `TcpChaosProxy`, `NetworkPartitionTarget`, and `withNetworkPartition` APIs remain available and do not
require migration. Do not stack a manual proxy over managed routing. Keep recovery assertions within the enclosing
system block, and serialize tests that share the same application.

### Lifecycle behavior

Stove rolls back resources when startup fails. Shutdown restores active faults, stops the application, closes its
managed routes, and disposes dependencies in reverse registration order. It attempts the remaining stages when a stage
fails. `Stove.close()` still logs cleanup failures instead of throwing; the first failure is logged with subsequent
failures suppressed. Database cleanup must also tolerate startup ending before its
client is initialized.

## Upgrade and operation

- Align the Stove libraries, tracing plugin, agent plugin package, and Stove Server on **0.28.0**.
- Profiling is disabled by default; existing tests do not start collecting unless enabled.
- IntelliJ users must delegate tests to the configured Gradle `Test` task for automatic attachment. Native Run Test does not execute the plugin's agent wiring.
- Shared ingress must forward `POST /ingest`, preserve `X-Stove-*` headers, and allow the server's 16 MiB upload limit. HTTPS certificate trust must be configured in the test JVM. Custom authentication headers are not exposed by the JVM profiling DSL yet; the Go wrapper accepts headers and a custom HTTP client.
- Profile tables are introduced by storage migration V12. Normal server migration handling applies for SQLite and PostgreSQL.
- Source builds now need Go (the version in `profiling-bridge/go.mod`) and a C toolchain for the embedded parser. Published server binaries bundle it, including third-party notices; downstream deployments need no Go service.
