# Stove MCP benchmark — 7 September 2026

Stove's MCP is fast enough for these local failure-triage fixtures, but the first
benchmark exposed a large context-cost bug and a snapshot retrieval bug. Both
are fixed. The result supports targeted evidence retrieval; it does not establish
production capacity or an agent's diagnostic accuracy.

The **before** build already contains the MCP efficiency refactor. The **after**
build additionally caps serialized JSON fields, resolves snapshot pointers before
truncation, and reports complete snapshot overview counts. This is not an
end-to-end comparison against the original implementation before the refactor.

## Method

- Apple M1 Pro, arm64, macOS 26.6.2; Rust 1.98.1, release build.
- Isolated temporary file-backed SQLite; 888 synthetic events ingested through
  the public protobuf HTTP endpoint. No pre-existing database was used.
- Five failed tests: assertion mismatch, duplicate-key database exception,
  unmatched mock request, timeout in a 400-span trace, and a 1,200-record catalog.
- Persistent HTTP/1.1 over loopback. Each case has three warmups and 60 timed
  requests. RTT ends after the entire body is read, excluding client JSON parsing
  and tokenization. The final run has 35 cases (2,100 timed sequential calls).
- Two short concurrent workloads: 240 calls each, eight clients, compact failure
  detail; one excludes and one includes the wide catalog.
- Actual token counts use `tiktoken 0.14.0`, `o200k_base`. Counts below describe
  the text fallback, not an assumption about how every client feeds MCP to a model.

## Measured improvements

| Case | Before text tokens | After text tokens | Before p95 | After p95 |
|---|---:|---:|---:|---:|
| Wide failure detail, tiny | 59,900 | 1,142 | 7.05 ms | 4.24 ms |
| Wide failure detail, compact | 59,900 | 1,221 | 7.08 ms | 3.77 ms |
| Entire wide snapshot, tiny | 59,358 | 396 | 5.19 ms | 3.42 ms |

The wide tiny detail costs **98.1% fewer tokens**. Previously, clipping every
string separately left wide objects effectively unlimited. Large fields now
return an explicit `truncated_json` preview. Small fields retain structured JSON.
These are field limits, not a hard cap on the whole tool response or server work.

| Ordinary failure detail | Tiny tokens | Compact tokens | Compact p95 |
|---|---:|---:|---:|
| Assertion mismatch | 1,074 | 1,136 | 0.88 ms |
| Database exception | 2,203 | 6,083 | 1.49 ms |
| Mock mismatch | 1,586 | 3,928 | 1.35 ms |
| Long trace timeout | 2,274 | 6,282 | 3.46 ms |

The exact seeded cause remains present in all **12 ordinary failure/budget
combinations**. This verifies evidence presence, not diagnostic reasoning.

## Recovery and error handling

The catalog diagnosis is intentionally beyond the first preview. It is absent
from failure detail under every budget after the fix. Retrieval remains possible:

| Follow-up | Text tokens | Result |
|---|---:|---|
| Snapshot `/catalog/sku_0999`, tiny | 419 | Still truncated before the diagnosis |
| Snapshot `/catalog/sku_0999`, compact | 419 | Complete selected record, including diagnosis |
| Snapshot `/catalog/sku_0999/diagnosis`, tiny | 380 | Exact diagnosis |
| Snapshot `/published/75`, tiny | 361 | Correct `{"order":75}` |

Before the fix, `/published/75` incorrectly returned `pointer_not_found` because
array truncation happened before pointer resolution. Pointers now resolve against
the full redacted structure, including escaped keys. Regression tests verify that
selection cannot bypass a sensitive ancestor and that missing pointers and
malformed JSON remain distinguishable.

Tiny wide detail plus a compact record follow-up totals **1,561 tokens across two
calls**, versus 59,900 in the old detail response. The record pointer is known to
the harness: this does **not** demonstrate that an agent can discover it unaided.
Equal token counts can hide different evidence, as the two 419-token record
responses show. Agents must inspect truncation markers.

All nine error probes passed: unknown argument, invalid budget, invalid limit,
invalid trace view, missing selector, missing run, unknown tool, malformed tool
call, and malformed JSON. Tool errors use `isError`; protocol errors retain their
JSON-RPC error codes. Successful text/structured responses matched, and the
synthetic secret did not appear in the measured tool responses.

## Latency and context costs

| Eight-client workload | Before p95 | After p95 | After p99 | Observed after requests/s |
|---|---:|---:|---:|---:|
| Ordinary failures | 18.86 ms | 17.62 ms | 30.21 ms | 905.5 |
| Including wide payload | 18.48 ms | 15.36 ms | 21.88 ms | 966.3 |

These are short client-observed bursts, not saturation or sustained-throughput
measurements. The small latency differences should not be treated as a proven
speedup. Local scheduling, client parsing and run-to-run noise affect the results.
Token reduction and corrected pointer results are the stronger findings.

Compact formatting alone uses roughly **29–33% fewer tokens** than equivalent
two-space pretty JSON for the four ordinary compact detail responses. That
comparison holds evidence constant. Fetching all four raw REST evidence kinds
costs much more, but that is an intentionally larger information set; selective
retrieval is not lossless compression of those responses.

Full long-trace detail still costs **25,963 tokens**. The compact exceptions view
costs **568 tokens** and retains the seeded exception (all three exception budgets
retain it). Start with tiny surveys/detail and ask for focused evidence when
needed; use full detail deliberately.

Both `structuredContent` and equivalent text are sent for client compatibility.
For example, compact long-trace detail costs about 6,300 text tokens but about
12,800 tokens if the entire wire envelope is tokenized. Actual model context cost
depends on client integration. The wire counts are recorded separately.

Remaining limits: no global response cap, complete stored JSON is still parsed
and redacted before previewing, and this dataset has only one run. PostgreSQL
scale, remote network latency, memory/CPU profiling, sustained ingestion, and
actual model diagnosis were not evaluated. The existing PostgreSQL load suite
remains a separate check.

## Reproduction and validation

[Run instructions](../acceptance-tests/README.md#mcp-failure-evidence-benchmark),
[benchmark harness](../scripts/benchmark-mcp.py), and
[recorded measurements](mcp-2026-09-07.json) are included. The measurement file
contains before/after binary hashes, host metadata, per-case sizes and percentiles,
cause-presence checks and error results. The harness also emits raw timings and
sample responses into its output directory. The final recorded run used
`target/mcp-benchmark/after-complete`; the baseline used `target/mcp-benchmark/before`.

Validation after the production fixes: **114 tests passed** (93 library, 14 MCP,
6 focused evidence, and 1 real-server agent-loop acceptance test). Formatting,
strict Clippy across all targets, and diff whitespace checks passed. The full
PostgreSQL acceptance/load suites were not rerun for this change.
